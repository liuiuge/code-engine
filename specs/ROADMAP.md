> 视角：Role 1 PM（`.workbuddy/agents/pm.md`）
> 性质：跨领域演进计划（`specs/NAME.md`）
> 目的：把 `PRODUCT_REVIEW.md`（商业化）与 `PRODUCTIONIZATION.md`（生产化）合并成一条
> **连贯的、分阶段、有出口标准的演进主线**。

---

## 0. 一句话主线

```mermaid
flowchart LR
    A[可用化<br/>生产化·本地自托管体验] --> B[能力扩展<br/>多语言 + 质量可信]
    B --> C[商业化<br/>云端 + 账号 + 计费]
```

**核心判断**：商业化不能建立在「用不下去」的工具上。先让它**好用**（阶段一），
再让它**能干更多**（阶段二），最后才谈**能卖**（阶段三）。
三个阶段是**因果依赖**，不是并列选项。

## 1. 三阶段总览

| 阶段 | 目标 | 时间视野* | 关键交付 | 出口标准（Gate） | 依赖 |
|------|------|-----------|----------|------------------|------|
| **一 · 可用化** | 把原型变成「用得下去」的真实工具 | 近期 1–2 月 | 实时进度(SSE)、流式生成、可取消、异步 Job、一键部署、可观测 | 用户在生成期间「有事做、能预期、能停」；`docker compose up` 即可用 | 无（基于现状） |
| **二 · 能力扩展** | 让它能干更多、且质量可信 | 中期 3–6 月 | 多语言后端、评测体系(pass@k)、verifier 类型/多解覆盖、题库广度 | 支持 ≥3 语言；有 pass@k 基准且可回归防劣化；verifier 覆盖主流题型 | 阶段一（需异步 Job + 可观测做底座） |
| **三 · 商业化** | 能对外提供服务并收费 | 远期 6 月+ | 云端 LLM + 自带 Key、账号+持久化、执行沙箱、计费/配额、数据合规、多租户扩展 | 多用户并发不互相影响；有计费与配额；生成代码在隔离环境执行 | 阶段二（能力够广、质量可信才能卖） |

\* 时间视野为规划估算，非承诺；按实际人力/模型供给调整。

## 3. 阶段二 · 能力扩展

> 承接阶段一，把「单语言原型」变成「多语言、质量可信」的引擎。

**交付物**
- **多语言后端抽象**（阶段一里商业化 P0 的「多语言」挪到此处——逻辑上它属于能力而非商业化，
  详见 §5 的 reconcilation 说明）。
  把 `executor.py` 的 Go 专用提取正则 / `go build` 抽象成 `extract / format / build / run` 接口，
  先补 Python，再 Java / C++。
- **评测体系（eval）**：pass@k 基准（用 LeetCode 官方测试集或自有题库），可回归防劣化。
  这是向用户/投资人证明「生成质量」的唯一硬证据，也是阶段三定价的基础。
- **verifier 覆盖扩展**：更多 `metaData` 类型、多解题容错（避免 two-sum 类误判）、未知类型显式降级提示。
- **题库广度**：更多题目、支持用户自有题目（为阶段三合规化铺垫）。

**出口标准（Gate 2）**
- 支持 ≥ 3 种语言，且每种语言的 compile + verify 闭环可用。
- 有可重复运行的 pass@k 基准，且每次模型/ prompt 改动可对比、防退化。
- verifier 覆盖主流题型（标量/数组/链表/树/多解），多解题不再误判。

## 4. 阶段三 · 商业化

> 详版见 `PRODUCT_REVIEW.md` 的 P0/P1。此处按依赖重新排列。

**交付物（依赖阶段二）**
- 云端 LLM 接入 + 用户自带 Key（脱离本地 Ollama 的硬约束）。
- 账号体系 + 持久化（历史、会话、配额）。
- 代码执行沙箱（容器/gVisor 隔离——阶段一单机自托管风险可控，规模化才必须）。
- 计费 / 配额 / 订阅档位；Token 成本与生成次数追踪。
- 题目数据合规化（授权题库或用户自有，规避 LeetCode ToS 风险）。
- 多租户 + 任务队列 + 弹性扩展。

**出口标准（Gate 3）**
- 多用户并发生成互不阻塞、互不越权。
- 有计费与配额 enforcement，成本可核算。
- 生成代码在隔离环境执行，单用户故障不波及宿主。
- 题目数据来源合规。

## 5. 与两份前置文档的关系（reconciliation）

- `PRODUCTIONIZATION.md` = 本 Roadmap 的 **阶段一**（原样采纳）。
- `PRODUCT_REVIEW.md` 的商业化 P0/P1 = 本 Roadmap 的 **阶段三**。
- **刻意调整**：`PRODUCT_REVIEW.md` 曾把「多语言」列为商业化 P0；
  在 Roadmap 中将其**下移**到 **阶段二（能力扩展）**。理由：多语言是产品能力边界，
  不是收费能力——一个 Go-only 工具既「用不下去」也「卖不出去」，应先扩能力再谈收费。
- **刻意调整**：`PRODUCT_REVIEW.md` 的「评测体系 pass@k」原为 P1；本 Roadmap 将其**上提**到
  **阶段二**，因为它是阶段三定价/承诺质量的先行证据，且能防模型/prompt 改动退化。

## 6. 风险与权衡

| 风险 | 影响阶段 | 缓解 |
|------|----------|------|
| 流式输出与超时守护的权衡 | 一 | 保留 wall-clock deadline（后台线程监控），到期中断流并 escalate |
| 多解题误判导致空跑/重生成 | 一/二 | 阶段一先修误判；阶段二做多解容错 |
| 评测基准建设成本高 | 二 | 先搭最小 pass@k（少量代表题），再扩 |
| 云端 LLM 成本不可控 | 三 | 阶段二 eval 已核算单题成本，阶段三据此定价 |
| 题目数据合规 | 三 | 阶段二即引入用户自有题目，降低对 LeetCode 抓取依赖 |
